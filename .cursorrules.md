# Proxyma - Agent Context & Reference Guide

This file serves as a condensed context window for AI agents. It summarizes the architecture, file layout, key modules, coding rules, and future direction of **Proxyma**, with direct file and symbol links to ensure rapid onboarding.

---

## 🎯 Project Overview & Goal
**Proxyma** is a distributed, heterogeneous P2P resource and compute orchestrator written in Go. Its goal is to unify devices (servers, desktops, mobiles) into a single mesh where hardware capabilities (compute tasks, storage, remote screen/camera) are transparently shared.

## 📌 Project Rules & Guidelines

### Go Coding & Compatibility Standards
* **Slice Boundary Guards**: Use explicit boundary guards (e.g., `if toDelete > len(keysToDelete)`) when trimming slices to guarantee clear bounds checking and maximum version compatibility.
* **Continuous Granularity Decomposition**: Maintain clean 3-tier continuous granularity. Decompose large monolithic files (`server.go`, `ServicesScreen.kt`, `PipelineEditor.kt`) into domain-specific modules and components.
* **Centralized Enums & Domain Methods**: Define all domain type constants (such as `ServiceType`) as string-backed enums in `internal/protocol/protocol.go` with helper methods (e.g. `(s ServiceSchema) IsStreaming() bool`). Never write ad-hoc string comparisons or manual config file re-reads in UI/binding wrappers (`cmd/proxyma-bind`) to infer domain behavior.
* **Stream Handler Channel Cleanup**: Always ensure streaming handlers (`BidiStreamHandler`) include `defer close(out)` at entry so channel receivers (`range out`) terminate cleanly upon stream completion.
* **Unified Multi-Mode Abstractions**: Prefer unifying execution modes (unary, streaming) into a single, clean function signature or interface (e.g. `ServiceHandler` with `.Execute()` and `.ExecuteStream()` helpers) over cluttering registries with multiple specialized handler fields or parallel structs.
* **In-Memory Registry Resolution (Zero Runtime Disk I/O)**: Never re-read or unmarshal configuration files (like `services.json`) during runtime API calls. Configuration files are read once at daemon startup or mutation time; runtime endpoints must resolve handlers and schemas directly from in-memory registries (`s.Compute.GetHandler`).
* **No Unrequested Commits**: Do not make git commits until explicitly requested by the user.

## 🔑 Key Workflows

### A. Pairing / Joining the Cluster
1. **Invite Generation**: A sponsor node generates a token via `proxyma invite` (handled by [InviteManager](file:///home/drusila/Projects/proxyma/internal/server/invite.go)).
2. **CSR Submission**: The client generates a private key/CSR and sends it to the sponsor (`/cluster/join`).
3. **mTLS Setup**: The sponsor signs the CSR via [tls.go](file:///home/drusila/Projects/proxyma/internal/p2p/tls.go#L95) and replies with node certificate, CA certificate, and current topology.
4. **mTLS Guard**: Inter-node traffic requires certificates and is authorized by [mTLSGuard](file:///home/drusila/Projects/proxyma/internal/server/handlers.go#L19).

### B. File Sync & VFS Replication
1. **Local Control**: `proxyma sync` commands the local daemon using a Unix domain socket (`proxyma.sock`) to execute a sync sequence, avoiding HTTP exposure (see [sync.go](file:///home/drusila/Projects/proxyma/cmd/proxyma/sync.go) and `handleUnixConnection` in [server.go](file:///home/drusila/Projects/proxyma/internal/server/server.go)).
2. **Manifest Processing**: The node fetches remote manifests, processes them via [StorageEngine](file:///home/drusila/Projects/proxyma/internal/storage/storage_engine.go#L17), and pushes missing entries to `downloadQueue`.
3. **Async Retrieval**: Dedicated workers download and write missing blobs in the background using `downloadWorker` in [vfs_sync.go](file:///home/drusila/Projects/proxyma/internal/server/vfs_sync.go).

### C. Compute Execution & Bidding
1. **Task Request**: An outgoing task is scheduled (`DispatchTask` in [compute_bridge.go](file:///home/drusila/Projects/proxyma/internal/server/compute_bridge.go)).
2. **Service Bid**: The client asks the cluster for bids matching the resource requirement. The best bid is selected based on a cost/performance strategy (Fastest, Cheapest, Low Power) defined in [protocol.go](file:///home/drusila/Projects/proxyma/internal/protocol/protocol.go#L105).
3. **Execution**: The target node runs the task via `script`/`exec` handler or a custom `gRPC` client stub using [handlerBuilder.go](file:///home/drusila/Projects/proxyma/internal/compute/handlerBuilder.go).

## 🔮 Future Direction & Roadmap

Based on open issues ([issues](file:///home/drusila/Projects/proxyma/issues) and [README.md](file:///home/drusila/Projects/proxyma/README.md)):
1. **Database Migration**: Shift the VFS metadata from BoltDB to BadgerDB to improve SSD write performance and handle large directories efficiently.
2. **Distributed Consensus**: Incorporate Raft or a similar consensus protocol to maintain uniform mesh state without a single coordinating authority.
3. **gRPC/Streaming**: Shift the JSON-based protocol to gRPC/Protobuf streams for high-throughput, low-latency node-to-node connection. Integrate WebRTC for raw data/streaming tasks.
